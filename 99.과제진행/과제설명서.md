## 0. 한눈에 보기

- **무엇을 하는가**: RRC_CONNECTED 상태의 UE를 RRC_INACTIVE로 보낼 때, **inactivity timer를 얼마로 줄지**와 **지금 INACTIVE로 보낼지/조금 더 연결을 유지할지**를 작은 신경망(GRU)이 추천한다.
- **AI가 내는 값 2가지**
  - `resume_prob` (0~1): "이 UE가 곧 다시 깨어날(resume) 확률". 높으면 → 연결 유지(INACTIVE 보류)가 유리.
  - `resume_time` (초): "다음에 깨어나기까지 예상 시간". 이 값으로 타이머를 정함 (`timer = resume_time × MARGIN`).
- **핵심 개입 1지점**: `FnVCCBAiClient_IsAbleToProceedInactive()` — InactivityNotification을 받았을 때 INACTIVE로 천이할지(=true) 보류할지(=false) 결정. `resume_prob ≥ 0.6`이면 보류하고 타이머를 연장.
- **안전장치**: 추론 실패/타임아웃이 누적되면 **Fallback**(기존 정적 타이머 로직)으로 자동 복귀. `g_aiEnabled=false`면 AI 결정을 완전히 끄고 legacy 동작.

## 1. 시스템 구조

### 1-1. GRU 모델 명세 (C++ 추론과 1:1 일치)

| 구성 | 사양 |
|---|---|
| 입력 1 (시퀀스) | `seq[10][2]` — 과거 최대 10회 resume 이력 (durationSec, resumeCause) |
| 입력 2 (정적) | `stat[15]` — 현재 호의 5QI/DRB/AMBR/RSRP/RNA/시각 등 |
| GRU | input_size=2, hidden_size=16, num_layers=1 (게이트 순서: reset \| update \| new) |
| MLP | Linear(15 → 16) + ReLU |
| 결합 | concat(GRU_out 16, MLP_out 16) = 32 |
| Head1 | Linear(32 → 1) + Sigmoid → `resume_prob` |
| Head2 | Linear(32 → 1) (선형) → `resume_time` |
| 총 파라미터 | **1,282개** |

> C++ 추론 엔진(`VccbAiEngine.cpp`)과 학습 모델(`train.py::RrcGruModel`)은 **구조·가중치 배열 레이아웃이 정확히 동일**해야 한다. 가중치는 `export_weights.py`가 `VccbAiWeights.h`로 내보낸다.

### 1-2. AI 개입 포인트 ①~⑤ (구현 완료)

| 포인트 | 위치 | 역할 | 상태 |
|---|---|---|---|
| **①** | `MsgE1apMake.cpp` → `VEIL_fillE1_Inactivity_Timer()` | E1AP BearerContext Setup/Modify 시 추천 타이머 주입 (`FnVCCBAiClient_RecommendInactivityTimer`) | ✅ |
| **②** | `FeatRrcInactive.cpp` → `FnVCCB_IsAbleToProceedRRCInactive()` | InactivityNotification 수신 시 즉시 INACTIVE 천이 vs 타이머 연장 판단. `false` 반환 시 `BearerContextModification` fire-and-forget 송신 | ✅ |
| **③** | `StateSaRrcInact.cpp` → `FnVCCB_Inact_ProcRRCResumeRequest1()` | RRCResume 수신 시 INACTIVE 지속시간·원인을 이력에 기록 (`FnVCCBAiClient_OnResumeRequest`) | ✅ |

## 3. 주요 상수 · 전역 통계 (`VccbAiClient.h`)

| 상수 | 값 | 의미 |
|---|---|---|
| `VCCB_AI_KEEP_THRESHOLD` | 0.6 | 이 값 이상이면 INACTIVE 보류(연결 유지) |

| `VCCB_AI_FALLBACK_COUNT` | 10 | 연속 실패 누적 시 Fallback 전환 |
| `VCCB_AI_INFER_TIMEOUT_US` | 1000 | 추론 타임아웃(µs) |
| `VCCB_AI_24H_WINDOW_SEC` | 86400 | resumeCount24h 윈도우 |

전역 통계(`VccbAiGlobalStats_type`, `FnVCCBAiClient_PrintStats()`로 출력): 총 요청/성공/실패/타임아웃/Fallback 수, 포인트별 호출 수, 평균 추론 시간, 연속 실패 수, Fallback 모드 여부.

입력 → preprocess.py → dataset.npz → train.py → model.pt → export_weights.py → VccbAiWeights.h → (C++ 재빌드)

### 5-2. `preprocess.py` (데이터 생성)

- **Method A (합성)**: 5QI별 3GPP 도메인 규칙(Log-Normal duration, RSRP/성공률 영향)으로 `N_SYNTHETIC`(기본 20000)개 샘플 생성. 학습 데이터의 본체.
- **Method B (gtest 실측)**: `VCCB_AI_DATA_FILE` CSV가 있으면 로드해 합성과 병합. 실제 `buildAiInput()`이 만든 feature 범위를 반영.
- 출력 시 `resume_prob=1 비율`, `resume_time mean/std`를 찍어 **라벨 균형**을 확인할 수 있다 (이상적 ~50%).
- 주요 조정 포인트: `N_SYNTHETIC`(env `VCCB_AI_SYNTH_N`), `PROB_HORIZON_SEC`(env `VCCB_AI_PROB_HORIZON`, 기본 60s), `FIVEQI_PROFILES`.

### 5-3. `train.py` (학습) — 정규화 fold 설계

raw feature는 스케일 편차가 크다(AMBR 10~2000, RSRP 0~127, duration 0~수백, 0/1 플래그…). 이를 그대로 넣으면 첫 Linear의 출력이 수백~수천이 되어 **sigmoid가 포화 → `resume_prob`이 입력과 무관하게 1.0으로 고정**되고 회귀도 붕괴한다.

**해결**: 학습은 정규화된 입력/타겟으로 하고, 그 정규화를 `export_weights.py`가 가중치에 되접어(fold) **C++은 여전히 raw 입력/raw 초 출력**을 쓰게 한다. (엔진·`buildAiInput()` 무수정)

- 고정 정규화 상수: `SEQ_MEAN/STD`(2), `STAT_MEAN/STD`(15), `TIME_MEAN/STD`. (도메인 기반, 데이터 의존 아님)
- `VccbDataset`에서 입력(seq/stat)·타겟(time) 정규화. `Y_prob`(0/1)은 그대로.
- **(v1.2.0)** `Y_time`을 `REG_CLIP_SEC=600`으로 클립 + 손실 `MSE → SmoothL1(Huber)` → 긴 꼬리 outlier가 시간 손실을 폭발시키지 않게 안정화.
- 하이퍼파라미터: EPOCHS=50, BATCH=256, LR=1e-3, Adam + CosineAnnealing.

### 5-4. `export_weights.py` (가중치 내보내기) — fold 수식

학습 모델은 정규화 공간에서 동작하므로, 아래를 첫 affine 층에 흡수한다:
- 입력: `W·((x-μ)/σ)+b = (W/σ)·x + (b − (W/σ)·μ)` → `GRU_WEIGHT_IH`/`GRU_BIAS_IH`, `MLP_WEIGHT`/`MLP_BIAS`
- 시간 출력 역정규화: `t = t_norm·σ_t + μ_t` → `HEAD_TIME_WEIGHT`/`HEAD_TIME_BIAS`
- `head_prob`(sigmoid 출력)과 `GRU_HH`는 **무변경**

수식이 정확히 동치라 C++ 결과는 학습과 일치한다. 실행 시 `Inference @feature-mean` 한 줄로 포화 여부를 자가 점검한다.

> ⚠ **`train.py`와 `export_weights.py`의 정규화 상수는 반드시 동일** (export가 train에서 import). 상수를 바꾸면 둘 다 재실행.

### 5-5. `run_all.sh`

`pip install -r requirements.txt` → `preprocess.py` → `train.py` → `export_weights.py`를 순서대로 실행하는 일괄 스크립트(`set -e`로 중간 실패 시 중단).

## 6. 학습 데이터 전략 (Method A + B) & 데이터 수집 로거

- 공개 데이터셋(Kaggle/HuggingFace 등)에는 gNB 내부 call-processing feature 조합이 없어 **의미가 불일치**한다 → 합성(A) + 실측(B)으로 자체 생성.
- **데이터 수집 로거** (`VccbAiClient.cpp`, `#ifdef VCCB_AI_DATA_COLLECT`): Resume 발생 시 history 갱신 **직전** `buildAiInput()`으로 feature 스냅샷 + 실측 레이블을 CSV 1행 emit. 운영 빌드에는 영향 없음(토글 OFF가 기본).
- CSV 스키마: `callId, seq0_dur, seq0_cause … seq9_dur, seq9_cause, stat0 … stat14, label_durationSec, label_resumeCause`
- 출력 경로: env `VCCB_AI_DATA_FILE` (기본 `/tmp/vccb_ai_dataset.csv`), append 모드.
- 빌드 토글: `VCCB/Makefile.body`, `VCCB/Test/ut/Makefile.body`에 `ifeq ($(VCCB_AI_DATA_COLLECT),1) → -DVCCB_AI_DATA_COLLECT` (기본 OFF).

- `SetUp()`은 셀/CHO/GNB 설정과 mock 기대치를 잡고, RRC Inactive 파라미터(`rrcInactiveTimer=20` 등)를 세팅.

- `storeCoreNetworkAssistanceInformationInInitialUeContextSetup`: NGAP CoreNetworkAssistanceInformation 저장 로직 검증(AI 무관). `TearDown()`에서 `SetEnabled(true)`로 기본값 복구.

**(C) `test_SaRrcInactive_AI` (AI 결정론적 단위 테스트, AI ON)**
- `SetUp()`: `Reset()` + `SetEnabled(true)`로 추론 경로 활성화.
- **TC1 `AiClient_extendCount_force_INACTIVE`**: `extendCount ≥ MAX(3)`이면 가중치와 무관하게 강제 INACTIVE(`true`) + 카운터 0 리셋. `SetEnabled(false)`면 항상 legacy로 진행됨도 확인.
- **TC2 `AiClient_fallback_returns_default_timer`**: history에 NaN을 주입해 추론 실패 10회 유발 → Fallback 진입 → 기본 타이머 그대로 반환.

## 8. ⭐ 핵심: 테스트 1개로 어떻게 데이터셋을 만드는가 (전체 그림)

> 이 프로젝트에서 가장 중요한 개념이라 따로 정리한다. "RRCSuspend 테스트 케이스 하나로 어떻게 학습 데이터를 만드는가?"라는 질문에 대한 답이다.

### 8-1. 먼저, 흔한 오해부터 풀기

**`test_SaRrcInactiveAI.json`의 `RRCSuspend_procedure` 테스트 케이스는 "학습 데이터를 만드는 것"이 아니다.**

| 무엇 | 진짜 역할 |
|---|---|
| JSON의 `RRCSuspend_procedure` 1개 | **회귀(regression) 테스트** — Conn→Inactive 진입 흐름이 깨지지 않았는지 확인. (이 테스트는 AI를 **끄고**(`SetEnabled(false)`) 돌린다) |
| 학습 데이터 생성 | **다른 곳**에서 한다 → 아래 8-2의 Method A + Method B |

즉, "테스트 케이스 하나"는 **흐름 검증용**이고, 학습 데이터는 **별도 경로**로 대량 생성한다. 둘을 혼동하면 안 된다.

### 8-2. 그러면 학습 데이터는 어디서 오나 — Method A + B

AI 모델 1개를 학습시키려면 보통 **수만 개의 샘플(= feature + 정답 한 쌍)**이 필요하다. 흐름 테스트 1번으로 나오는 1~2개로는 절대 부족하다. 그래서 두 방법을 합친다.

**Method A — 합성 데이터 (`preprocess.py`, 주력)**

- 3GPP 도메인 규칙으로 **가상의 호 2만 개**를 컴퓨터가 만들어낸다 (`N_SYNTHETIC=20000`).
- 5QI(서비스 종류)별로 "이런 서비스는 보통 이 정도 지속시간/RSRP/성공률"이라는 규칙(`FIVEQI_PROFILES`)을 두고, 거기에 난수를 섞어 다양한 호를 생성.
- 예: VoNR(5QI=1)은 짧게, 기본 베어러(5QI=9)는 길게… 같은 통계 분포.
- **장점**: 실측 없이도 대량·다양한 데이터 확보. **단점**: 실제 gNB 값 범위와 미세하게 다를 수 있음 → 그래서 B로 보정.

**Method B — gtest 실측 sweep (`test_SaRrcInactiveAI.cpp`의 `AiClient_DataCollect_Sweep`)**

- 여기가 "테스트로 데이터 만드는" 진짜 부분인데, **JSON 흐름이 아니라 C++ 코드가 파라미터를 직접 바꿔가며** 만든다.
- 아래 파라미터를 **전수 조합(곱집합)**으로 돌린다:

| 파라미터 | 값 후보 | feature |
|---|---|---|
| 5QI | 1, 2, 5, 7, 8, 9 (6개) | stat[0] |
| DRB 수 | 1, 2, 4 (3개) | stat[1] |
| AMBR | 100, 600, 2000 Mbps (3개) | stat[2] |
| GBR 유무 | 0, 1 (2개) | stat[3] |
| RSRP | 40, 75, 110 (3개) | stat[6] |
| RNA 셀 수 | 1, 8 (2개) | stat[8] |
| resumeCause | 0~4 (5개) | resumeCause |

- 조합 수 = 6×3×3×2×3×2×5 = **약 3,240행**.
- 각 조합마다 실제 `buildAiInput()` 경로를 그대로 타서 feature를 뽑고, `OnResumeRequest()`를 불러 **CSV 1행**을 남긴다 (`VCCB_AI_DATA_FILE`).
- **왜 JSON이 아니라 C++ sweep인가**: 5QI/AMBR/RSRP 같은 값은 녹화된 Attach 시나리오에 **고정**되어 있어 JSON만으로는 못 바꾼다. C++에서 `callInfo_type`에 직접 세팅하면 자유롭게 sweep하면서도 **운영과 똑같은 추출 경로**를 검증할 수 있다.

> **정리**: `preprocess.py`가 합성 2만 개(A) + gtest CSV 약 3,240행(B)을 **하나로 병합** → `dataset.npz`. 이게 학습 입력이다.

### 8-3. "정답(label)"은 무엇인가

각 샘플에는 feature와 함께 **정답 2개**가 붙는다 (모델이 맞혀야 할 값):

| 정답 | 의미 | 생성 방법 |
|---|---|---|
| `Y_time` | 이 UE가 INACTIVE로 얼마나 오래 있다 깨어났나 (초) | 합성: 5QI별 분포에서 샘플 / 실측: 실제 측정 duration |
| `Y_prob` | "곧 깨어났나?" (`duration < 60s`이면 1, 아니면 0) | `Y_time`을 임계값(`PROB_HORIZON_SEC=60`)과 비교 |

모델은 feature를 보고 이 `Y_time`(→ `resume_time`)과 `Y_prob`(→ `resume_prob`)을 예측하도록 학습된다.

### 8-4. 언제, 얼마나, 어떻게 학습(training)하나

- **언제**: **오프라인**으로, **데이터셋이 바뀔 때만** 사람이 수동 실행한다. (운영 중 자동 재학습 없음 — 온라인 학습 아님)
  - 예: 새 sweep 데이터를 모았을 때, 합성 규칙을 바꿨을 때, feature를 추가했을 때.
- **주기**: 정해진 주기는 없다. "데이터/규칙 변경 → 1회 재학습 → 가중치 반영 재빌드"가 한 사이클.
- **얼마나(횟수)**: 한 번의 학습에서 `EPOCHS=50` (전체 데이터를 50번 반복 학습). batch=256, Adam, LR=1e-3.
- **어디서**: 빌드 서버 host의 venv (docker 밖). GPU 불필요(CPU로 수십 초~수 분).
- **결과물**: `model.pt` → `export_weights.py`로 `VccbAiWeights.h` 생성 → C++ 재빌드 시 포함.

> 핵심: **학습은 가끔(데이터 바뀔 때) 한 번씩**, 추론은 **호 처리 때마다 실시간**. 둘은 완전히 분리된 단계다.

### 8-5. 추론(inference)은 운영 중 언제 실행되나

추론은 "E1으로 inactivityTimer 전달할 때만" 도는 게 **아니다.** 운영 빌드에서 **3개 지점**에서 실시간 호출된다 (각 1ms 타임아웃, 실패 시 Fallback):

| 시점 | 함수 (포인트) | 추론으로 결정하는 것 |
|---|---|---|
| **① E1 타이머 채울 때** | `RecommendInactivityTimer` (포인트①) | BearerContext Setup/Modify의 inactivityTimer 추천값 |
| **② InactivityNotification 받을 때** | `IsAbleToProceedInactive` (포인트②) | 지금 INACTIVE로 보낼지(true) vs 타이머 연장하고 보류할지(false). `resume_prob≥0.6`이면 보류 |
| **④ RNA Update 받을 때** | `OnRnaUpdate` (포인트④) | resume_prob 기반 RNA 크기 권고(로그) |

> 포인트③(`OnResumeRequest`)·⑤(`SeedFromXnapHistory`)는 추론이 아니라 **이력 기록/seed** (관측 단계). 이 관측 덕분에 다음 추론의 입력(`history[]`, `resumeCount24h` 등)이 채워진다.
>
> 즉 추론은 **호 하나가 살아가는 동안 여러 번** 일어날 수 있고(타이머 세팅 시, 연장 판단 시, RNA 갱신 시), 그 중 핵심 결정은 **②번(진입/연장 판단)**이다.

### 8-6. 전체 흐름 한 장 요약

```
[데이터 만들기 — 가끔, 오프라인]
  preprocess.py
    ├─ Method A: 합성 호 20,000개 (5QI 도메인 규칙)
    └─ Method B: gtest sweep CSV ~3,240행 (5QI×DRB×AMBR×GBR×RSRP×RNA×cause)
        → 병합 → dataset.npz  (feature + 정답 Y_time/Y_prob)

[학습 — 데이터 바뀔 때 1회]
  train.py (50 epoch) → model.pt → export_weights.py → VccbAiWeights.h
                                                            │
[빌드 — 가중치 반영]                                         ▼
  make ... (VccbAiWeights.h 포함)

[추론 — 운영 중 호마다 실시간]
  포인트① 타이머 추천 / 포인트② 진입·연장 판단 / 포인트④ RNA 권고
  (관측: 포인트③ resume 이력, 포인트⑤ HO seed → 다음 추론 입력에 반영)
```

> **그래서 "테스트 1개"의 정체**: `RRCSuspend_procedure`(JSON)는 **진입 흐름이 안 깨졌나 확인하는 회귀 테스트**일 뿐이고, 학습 데이터는 합성(A) + C++ sweep(B)이 대량으로 만든다. 이 둘을 분리해서 이해하는 것이 이 프로젝트의 핵심이다.

## 9. 학습에서 일어나는 일

학습은 "예측이 정답에 가까워지도록 가중치를 조금씩 고치는 것"의 반복이다.

### 9-1. 용어

- **샘플 / 데이터셋**: 한 줄(한 호의 feature + 정답)이 샘플. 전체를 학습용 85% / 검증용(Val) 15%로 나눈다.
- **epoch(에폭)**: 학습 데이터 **전체를 한 번 다 본 것**. 50 epoch = 50번 반복 학습.
- **batch**: 한 번에 256개씩 묶어 처리(메모리·속도 때문).
- **sweep(스윕)**: 어떤 파라미터의 값을 **한 개만 고정하지 않고 여러 값으로 훑어보는 것**.  
  예를 들어 `5QI={1,2,5,7,8,9}`, `DRB={1,2,4}`, `RSRP={40,75,110}`처럼 후보 집합을 정하고,  
  조합을 모두 실행해 데이터를 모은다(전수 조합 sweep). 이 프로젝트의 `AiClient_DataCollect_Sweep`이 여기에 해당한다.
- **loss(손실)**: 예측이 정답과 **얼마나 틀렸는지**를 하나의 숫자로. **작을수록 좋다.**
- **gradient/optimizer(Adam)**: loss를 줄이는 방향으로 가중치를 조금씩 이동.

### 9-2. 출력 표의 각 열 의미

```
Epoch      Train        Val   P_loss   T_loss
   25     0.2868     0.2940   0.2857   0.0167 *
```

| 열 | 의미 | 좋은 방향 |
|---|---|---|
| **Epoch** | 몇 번째 전체 반복인지 | — |
| **Train** | 학습셋 평균 loss (= P_loss + 0.5×T_loss). 모델이 **학습 데이터**에 틀린 정도 | 감소 |
| **Val** | 검증셋(학습에 안 쓴 15%) 평균 loss. **처음 보는 데이터**에 대한 일반화 성능 → 가장 중요한 지표 | 감소 |
| **P_loss** | `resume_prob` 분류 손실(BCE). "곧 resume할지"를 맞히는 정확도 | 0에 가깝게 |
| **T_loss** | `resume_time` 회귀 손실(Huber, **정규화 단위**). resume_prob=1인 양수 샘플에서만 계산 | 작게 |
| **`*`** | 지금까지 중 **Val loss 최저(best)를 갱신**한 epoch. best 모델만 `model.pt`로 저장 | — |

### 9-3. 손실 함수 설명 (BCE · Huber)

**BCE (Binary Cross Entropy) — P_loss에 사용**

`resume_prob`처럼 **0 또는 1 둘 중 하나**를 예측할 때 쓰는 손실 함수.

- 정답이 1(곧 resume)인데 모델이 0.1이라고 하면 → **큰 벌점**
- 정답이 0인데 모델이 0.9라고 하면 → **큰 벌점**
- 모델 출력이 정답 방향에 가까울수록 BCE가 0에 가까워짐

쉽게 말해: "확률 예측을 얼마나 정답답게 했는지 재는 점수".  
분류 문제의 가장 기본적인 손실 함수라 `P_loss`에 그대로 씀.

**Huber Loss (SmoothL1) — T_loss에 사용**

`resume_time`처럼 **연속적인 숫자(회귀)**를 예측할 때 쓰는 손실 함수.  
MSE(평균 제곱 오차)의 단점을 보완한 "절충형"이다.

| 오차 크기 | MSE | Huber |
|---|---|---|
| 작을 때 | 제곱 벌점 (정밀) | 제곱 벌점 (동일) |
| 클 때 (이상치) | 제곱이라 **폭발** | 선형 벌점으로 **억제** |

→ duration이 0~수백 초로 꼬리가 긴 이 데이터에서, MSE를 쓰면 긴 케이스 몇 개가  
손실을 수천~수백만으로 폭발시킨다. Huber는 큰 오차를 선형으로 처리해 **안정적으로 수렴**.

**T_loss를 resume_prob=1 샘플에서만 계산하는 이유**

"곧 resume 안 할 케이스(`Y_prob=0`)"까지 시간 예측을 강하게 학습시키면 오히려 회귀가 흐려짐.  
어차피 "오래 있을 UE"는 타이머 추천에 별 의미가 없으므로, **곧 resume할 케이스만** 시간을 정밀하게 학습.

### 9-4. 어떻게 읽나

- **`*`가 붙은 줄** = 그 epoch이 역대 최고 성능(Val 기준). `*`가 없는 줄 = 직전 best보다 안 좋아서 저장 안 함(요동/과적합 신호일 수 있음). 끝에서 best 모델을 다시 불러와 저장한다.
- **Train ≈ Val로 같이 감소하다 평평해짐** = 정상 수렴. Val이 다시 오르면 과적합.
- **Train이 수천~수백만으로 들쑥날쑥** = 입력 스케일/타겟 outlier 문제. 본 프로젝트는 **정규화(v1.1.0) + 타겟 클립·Huber(v1.2.0)**로 해결 → 현재는 0.3 부근에서 매끄럽게 수렴.
- **T_loss 정규화 단위 → 초 환산**: SmoothL1/MSE 값에 대략 `√loss × TIME_STD(60)` 정도가 시간 오차(초)의 감.

### 9-5. 정상 학습 예시(v1.2.0)

`resume_prob=1 비율 55.4%`(균형 OK), Train/Val 0.29 부근 매끄럽게 수렴, `export` 자가점검 `resume_prob≈0.69`(1.000 아님)·`resume_time≈37s`(현실적) → **포화 해소 + 안정 회귀** 확인.

## 14. 코드 리뷰 버그픽스 (2026-06-03)

> 코드 리뷰에서 발견·수정한 결함 기록. 두 건 모두 **추론 동작과 gtest 통과**에 직접 영향을 준다.

### 14-1. 🔴 (Critical) `aiCtx` 미초기화 — 운영 빌드 AI 영구 Fallback + TC3 실패

**증상**
- `VccbAiEngine.h`의 `VccbAi_InitContext()`는 *"0xFF memset 직후 반드시 호출"* 이 전제인데, 전 소스트리에서 **호출처가 한 군데도 없었다.**
- `VLIB_InitCallInfo()`(`FeatCallInfo.cpp`)는 `callInfo_type` 전체를 `memset(…, 0xFF, …)` 한다 → `aiCtx`도 전부 `0xFF`로 채워짐.

**영향**
- `aiCtx.resumeSuccessRate` / `avgDurationSec` / `h[]` = `0xFFFFFFFF`(float NaN), `count` / `writeIdx` = `-1`.
- 운영 빌드: `buildAiInput()`이 `stat[9]/[11]/[12]`에 NaN을 채움 → `FnVCCBAiEngine_Infer()`의 `isfinite()` 검사 실패 → 매 추론 실패 → 10회 후 `g_fallbackMode=true` **영구 고착** → AI 가변 타이머가 **한 번도 적용되지 않고** 항상 정적 default 반환(과제 목표 무력화).
- gtest `TC3 (AiClient_OnResumeRequest_resets_extendCount)`: `ASSERT_EQ(count, 0)` 즉시 실패, `OnResumeRequest()` 내부 `history[writeIdx=-1]` **배열 범위 밖 쓰기(UB)**, `resumeSuccessRate` NaN으로 `ASSERT_FLOAT_EQ(…, 1.0f)` 실패. → §10-6 체크리스트 ⑤ `[PASSED] 5 tests` 불가.

**수정** (`VCCB_FEAT/RESOURCE/src/FeatCallInfo.cpp`)
- 상단에 `#include "VccbAiEngine.h"` 추가.
- `VLIB_InitCallInfo()`의 `0xFF` memset 직후 `VccbAi_InitContext(&ptCi->aiCtx);` 호출 추가 — `aiCtx`를 `memset(0)`하고 `resumeSuccessRate=1.0`(cold start) 시드.

### 14-2. 🟡 (Major) 포인트①의 `extendCount++` — 조기 강제 INACTIVE

**증상**
- `FnVCCBAiClient_RecommendInactivityTimer()`(포인트①, `VccbAiClient.cpp`)의 KEEP 분기가 `ptCi->aiCtx.extendCount++`를 수행.

**영향**
- 포인트①(`VEIL_fillE1_Inactivity_Timer`)은 **DRB마다·PDU Session마다** 호출된다(`MsgE1apMake.cpp` 9076/9288/10343/10937/11095/11507 등). DRB 3개짜리 호면 BearerContextSetup 한 번에 `extendCount`가 곧장 `MAX_EXTEND_COUNT(3)`에 도달 → 포인트②의 첫 InactivityNotification에서 추론 없이 **강제 즉시 INACTIVE**. "연장 횟수"의 의미와 어긋남.

**수정** (`VccbAiClient.cpp`)
- 포인트①에서 `extendCount++` 제거(주석으로 사유 명시). `extendCount`는 실제 연장(deferral) 이벤트인 **포인트②(`FnVCCBAiClient_IsAbleToProceedInactive`)에서만** 증가하도록 일원화.

### 14-3. 🟢 (Minor) 테스트 주석 정정

- `test_SaRrcInactiveAI.cpp` TC3의 `resumeCause` 주석 *"1 = mo-Data"* 는 NR RRC `ResumeCause` 인코딩과 불일치(실제 mo-Data=4). 단정 로직(emergency 외 전부 success)에는 영향 없으나, 혼동을 피하도록 "non-emergency(emergency=0만 실패 처리)"로 주석만 정정.

> **검증 안내**: 위 수정 후 docker 빌드(`make … RT_OPTION=test_SaRrcInactive`)에서 `TC1/TC2/TC3 + JSON 회귀 2건 = [PASSED] 5 tests`가 충족되고, 운영 경로의 AI 가변 타이머가 정상 동작해야 한다. (본 리뷰 환경에는 크로스컴파일 toolchain이 없어 정적 분석으로 도출한 결론이며, 실제 빌드/실행 검증은 대상 VM에서 수행 필요.)

## 15. 기술 Q&A (현재 구현 기준, 2026-06-03)

> 코드 리뷰 과정에서 오간 핵심 질문/답변을 구현 사실에 근거해 정리한다.

### 15-1. (Q1) 각 상태값은 어떤 "기준"으로 timer를 계산하나 / 이게 50 epoch training인가 / 데이터 출처

- **명시적 규칙은 코드에 없다.** C++ 추론에는 "5QI=1이면 20초" 같은 if 규칙이 전혀 없다. 각 상태값의 기준은 **학습된 가중치(`VccbAiWeights.h`)에 분산 저장**되어 있고, 추론은 `buildAiInput()` → forward 1회 → `resume_time` → `× 1.2`가 전부다.
- **"기준"의 출처는 `preprocess.py`의 합성 규칙(Method A)**이다. 현재 라벨에 실제로 반영되는 관계:
  - **5QI**: `FIVEQI_PROFILES`의 평균 지속시간 — 1→20s, 2→30s, 5→45s, 7→90s, 8→150s, 9→200s (5QI 클수록 timer 길게). 가장 강한 신호.
  - **RSRP**: `rsrp_factor = 1 + (75 − RSRP)/150` (≈0.65~1.5) — 신호 약할수록 재접속 늦다고 보고 timer 길게.
  - **재접속 성공률**: `hist_factor = 1 − 0.3×(success_rate − 0.5)` — 성공률 높으면 짧게. 시퀀스 이력은 GRU가 처리.
  - **DRB·AMBR·GBR**: 입력 feature로는 들어가나 **합성 라벨 식(`next_dur`)에 미반영** → 모델이 거의 학습하지 못함. (실측 또는 합성 규칙 보강 필요 — §15-4)
- **50 epoch training과는 별개다.** 추론(운영 중, 호마다, 1ms, forward 1회) ≠ 학습(오프라인, `train.py`, 데이터 바뀔 때만 50 epoch). 호 처리 때마다 50 epoch 도는 게 아니다.
- **데이터 출처**: 현재는 **합성(Method A) 전부**(`N_SYNTHETIC=20000`, 3GPP 도메인 규칙). Method B(gtest CSV)는 있으면 자동 병합되나 미수집 상태.

### 15-2. (Q2) resume_prob / resume_time 사용처 / 왜 × 1.2

- **resume_prob가 분기 결정의 핵심, resume_time은 사실상 한 분기에서만 사용**된다(`VccbAiClient.cpp`).
  - 포인트① `RecommendInactivityTimer`: `prob ≥ 0.6` → `timer = resume_time × 1.2` (**여기서만 resume_time 사용**) / `prob ≤ 0.3` → `timer = 1초`(조기 해제) / 그 사이 → `defaultTimer`(정적값 유지).
  - 포인트② `IsAbleToProceedInactive`: `prob ≥ 0.6` → `false`(INACTIVE 보류·연장·BearerContextModification 송신), 아니면 `true`(즉시 INACTIVE).
  - 포인트④ `OnRnaUpdate`: prob로 RNA 크기 권고 로그.
- **× 1.2 = `VCCB_AI_MARGIN_FACTOR`, 안전 여유.** 예측이 부정확하므로 예측값보다 20% 길게 잡아 "UE가 깨어나기 직전 타이머 만료 → 조기 해제 → 재접속 시그널링 폭증"을 방지. 학습값이 아닌 도메인 상수라 조정 가능.

### 15-3. (Q3) GRU → LSTM 변경 범위 / 도입 판단

- **변경 범위(중간)**: `train.py` `nn.GRU→nn.LSTM`(2~3줄), `export_weights.py` 게이트 3→4개·배열 크기 변경(IH 96→128, HH 768→1024, bias 48→64; ~15~20줄), `VccbAiEngine.cpp` `gru_step→lstm_step`(셀 상태 `c[16]` 추가, ~30줄), `VccbAiWeights.h` 자동 재생성. **`aiCtx` 구조체 변경 불필요**(추론은 매번 h=0,c=0에서 시퀀스 재실행). 파라미터 1,282→약 1,602개.
- **선택 구동**: 빌드타임 토글(`-DVCCB_AI_MODEL_LSTM`, 권장) 또는 런타임 선택(두 가중치 세트 동시 탑재 + 디스패치, 무거움).
- **도입 판단: 보류(구현하지 않음).** 이유 — ① 시퀀스가 ≤10스텝·feature 2개로 매우 짧아 LSTM의 장기 의존성 이점이 사실상 없음(짧은 시퀀스에선 GRU가 동등하거나 유리), ② 예측 주력은 GRU가 아니라 정적 feature의 MLP 경로라 순환셀 교체는 영향 가장 작은 부품 손보기, ③ 게이트 3→4개로 1ms 예산에서 지연만 증가, ④ 진짜 병목은 모델이 아니라 데이터(합성-only, DRB/AMBR/GBR 무신호, stat[4][5][7]=0). 같은 노력은 §13/§15-4/§15-5에 투자하는 편이 정확도에 훨씬 기여.

### 15-4. (Q) DRB/AMBR/GBR "실측 확보" 시 어떤 형태의 데이터를 수집하나

- **새로운 "bearer 생성/해제 이벤트 시계열"을 따로 수집하는 게 아니다.** 이미 구현된 로거(`aiDataCollectEmit()`, `#ifdef VCCB_AI_DATA_COLLECT`)가 필요한 형태를 그대로 emit한다: **Resume 이벤트마다 1행 = [INACTIVE 진입 시점의 feature 스냅샷] + [실측 라벨]**.
  - feature 스냅샷에는 이미 `stat[0]=5QI`, `stat[1]=drb_count`, `stat[2]=AMBR`, `stat[3]=has_gbr`가 포함 → DRB/AMBR/GBR은 **feature로는 이미 잡힌다.**
  - 실측 라벨 = 그 호가 **실제로 INACTIVE에 머문 시간**(`durationSec = Resume시각 − inactiveEntryTs`) + `resumeCause`. 합성과 달리 라벨이 그 호의 bearer 프로파일과 **자연스럽게 짝지어진다.**
- 즉 수집 단위는 "특정 시각 bearer 몇 개 생성/해제"가 아니라 **호 단위로 (bearer 프로파일 + 다음 재접속까지 걸린 시간)** 쌍이다. 사용자가 말한 "DRB 개수"는 스냅샷 feature의 일부로 이미 포함되며, 핵심 타깃(label)은 "그 프로파일에서 다음 resume까지의 시간"이다.
- **방법**: `VCCB_AI_DATA_COLLECT=1` 빌드로 실제 트래픽(또는 bearer 조합이 다양하게 나오는 현실적 시나리오) 구동 → CSV(`VCCB_AI_DATA_FILE`) 누적 → `preprocess.py`가 자동 병합 → 재학습. (gtest sweep은 값을 인위적으로 세팅하므로 "계약 검증/범위 확보"용이고, 진짜 통계 관계는 실트래픽에서 와야 한다.)
- **정직한 전제**: DRB/AMBR/GBR이 실제로 INACTIVE 체류시간과 상관이 없다면 아무리 모아도 예측력은 생기지 않는다. 수집의 목적은 "그 상관이 존재하는지"를 데이터로 드러내는 것.
- **라벨 정밀도 주의**: `durationSec`는 `inactiveEntryTs` 기준이다. 현재 이 타임스탬프는 포인트①(E1 타이머 채울 때)·포인트②(연장 분기)에서 찍히므로 대략 INACTIVE 진입과 일치하나, 정밀 라벨을 원하면 **실제 RRC_INACTIVE 진입 지점에서 스탬프되는지** 확인 권장.

### 15-5. (Q) `stat[4][5][7]` 실제 필드 매핑 — 무엇을, 어떻게 전달하나

| 인덱스 | feature | 3GPP 출처 | 변환 |
|---|---|---|---|
| 인덱스 | feature | 3GPP 출처 | 현황/판단 |
|---|---|---|---|
| stat[4] | cn_expected_idle_period | NGAP **ExpectedUEBehaviour** → ExpectedUEActivityBehaviour → `expectedIdlePeriod` (TS 38.413) | ❌ **현 망 AMF가 미전달 → 매핑 불가, 0 유지** |
| stat[5] | cn_stationary | NGAP **ExpectedUEBehaviour** → `expectedUEMobility` (ENUM) | ❌ **현 망 AMF가 미전달 → 매핑 불가, 0 유지** |
| stat[7] | neighbor_cell_count | RRC **MeasurementReport** → measResults 이웃셀(measResultNeighCells, NR/EUTRA) | ✅ **AMF 무관(gNB 보유) → 매핑 가능, 우선 진행** |

- **⚠ stat[4]·stat[5]는 현재 망 AMF가 ExpectedUEBehaviour IE를 보내지 않으므로 채울 방법이 없다.** 이 정보는 AMF→gNB CN assistance 전용이라 gNB에 다른 출처가 없다. 따라서:
  - **(권장) 0 슬롯 유지** — 작업 0. 학습 시 모델이 두 입력의 가중치를 ~0으로 학습해 무시한다. 추후 AMF가 ExpectedUEBehaviour를 전달하기 시작하면 그때 채운다.
  - (대안) 입력에서 제거 — `VCCB_AI_STATIC_INPUT` 15→13 + `buildAiInput()`·`preprocess.py`·`STAT_MEAN/STD` 정렬 + 재학습. 깔끔하나 죽은 입력 제거일 뿐 정확도 이득 없음.
  - 참고: stat[4](expected idle period)는 gNB가 관측으로 만든 `avgDurationSec`(stat[9]/[12])이 유사 역할을 하므로 손실이 거의 없다.
- **→ 실제 매핑 가치가 있는 건 stat[7] 하나뿐이다**(RRC MeasurementReport, AMF 무관). stat[4][5]는 placeholder로 둔다.
- **코드 주석 참고**: 주석은 stat[4][5]가 "NGAP CoreNetworkAssistanceInformation에 없다"고 했는데, 규격상으론 별도 IE인 ExpectedUEBehaviour에 존재한다. 다만 **현 배포 AMF가 그 IE 자체를 전송하지 않아** 결과적으로 0이 맞다.
- **전달 방식(3단계, stat[7]에만 적용)**:
  1. **파싱·저장(C++)**: RRC MeasurementReport 처리 핸들러에서 이웃셀 개수를 세어 `callInfo`의 호 단위 카운터에 저장. 보고 없으면 0.
  2. **읽기(`buildAiInput()`)**: `input->stat[7]=0.0` 하드코딩을 저장 필드로 교체.
  3. **Python 동기화**: `preprocess.py::gen_synthetic`의 stat[7]을 현실적 분포로 생성(현재 0 고정), `train.py`/`export_weights.py`의 `STAT_MEAN`/`STAT_STD` 인덱스 7을 placeholder(μ=0,σ=1)에서 실제 평균/표준편차로 교체 후 **재학습 + 재export**. (stat[4][5]는 AMF 미전달이라 0 유지 — 위 참조)
- **상수 주의(정정)**: `stat[4][5][7]`은 **이미 15개 슬롯 안에 잡혀 있으므로 `VCCB_AI_STATIC_INPUT(15)`를 늘릴 필요 없다.** 빈 슬롯을 채우는 것뿐. (§2 각주의 "상수를 늘려야" 문구는 16번째 이후 **신규** feature를 추가할 때만 해당.)
