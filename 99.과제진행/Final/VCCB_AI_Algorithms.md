## 1. 가상 dataset은 어떻게 생성하나? — `synth_data_gen.py`

### 한 줄 요약
**"가상의 UE 개체군을 만들어서, 각 UE가 시간에 따라 겪는 INACTIVE↔RESUME 이벤트 이력을 시뮬레이션"**하는 방식입니다. 단순히 feature 값들을 무작위로 조합해서 나열하는 게 아니라, UE 한 명 한 명이 "살아 움직이는" 것처럼 시간 순서대로 이벤트를 만들어냅니다.

### 왜 이렇게 만드나 (기존 방식의 한계)
기존 gtest sweep 방식은:
1. feature들을 서로 독립적으로 뽑음 (UE별 상관관계 없음)
2. 라벨을 사람이 손으로 짠 수식으로 정함 (행동 기반이 아님)
3. seq[](이력)에 실제 시간적 흐름이 없음

→ 이 3가지 문제를 해결하려고 "가상 UE 시뮬레이션" 방식을 새로 만듦.

### 생성 절차 (4단계)

**① Persona(행동 원형) 4종 정의**

| Persona | 비중 | 특징 |
|---|---|---|
| iot_sensor | 45% | 어쩌다 한 번 깨는 저빈도 IoT 센서 |
| bursty_phone | 35% | 자주 켰다 껐다 하는 일반 스마트폰 |
| fwa_fixed | 12% | 고정형 라우터(FWA), 트래픽량 매우 큼 |
| commuter | 8% | 이동이 잦은 통근자, 무선환경 변동 큼 |

**② UE 1명당 "고정 특성"을 딱 한 번 뽑음**
- 5QI, DRB 개수, AMBR, GBR 여부, RNA 셀 수
- **secondary_5QI**: 40% 확률로 "2번째 서비스 클래스"를 가짐 (예: 데이터용 + 영상통화용 베어러를 동시에 가진 UE)
- **24시간 핸드오버 횟수**: 대부분 UE는 적게, 소수만 매우 많이 움직임(지수분포)

**③ 이 UE의 "라벨 배율" 계산**
- `svc_factor` = 지연에 민감한 2차 서비스(영상통화 등)가 있으면 0.7배 (→ 더 빨리 재접속)
- `mob_factor` = 핸드오버가 많을수록 배율 감소 (→ 자주 이동하는 UE는 더 빨리 재접속)
- 이 둘을 곱해서 "라벨(다음 inactive 지속시간)"에 반영 → **"바쁘고 이동 많은 UE는 짧게 잔다"**는 도메인 지식을 데이터에 심는 것

**④ 이 UE의 세션 타임라인을 순서대로 시뮬레이션**

한 UE가 예를 들어 15번의 RESUME 이벤트를 겪는다면, 그 15번을 시간 순서대로 하나씩 생성:

```
다음 inactive 지속시간 = Weibull분포 샘플 × svc_factor × mob_factor
resumeCause = 전체 비율(응급 6% / 시그널링 32% / 착신 29% / RNA갱신 19% / 기타 14%)에서 추첨
```

- **RNA_UPDATE 원인이면 행을 만들지 않고 건너뜀** — 실제 C++ 코드가 RNA 갱신에 의한 resume은 이력에 안 쌓기 때문에, 데이터도 똑같이 맞춰줌 (안 그러면 학습/실전 데이터가 서로 달라짐)
- **seq[](과거 10개 이력)**: 이 UE 자신이 "실제로 이전에 겪은" 이벤트들로 채움 (다른 UE와 섞이지 않음, 시간 순서 유지)
- **평균 지속시간 / 성공률**: 실제 C++ 엔진과 똑같은 방식(지수이동평균, α=0.1)으로 매 이벤트마다 갱신
- **RSRP(신호세기)**: 매 세션마다 새로 흔들림 → 무선 환경이 계속 변하는 걸 흉내
- 한 행을 "찍은 시점" 기준으로 라벨을 기록 (그 이후에야 이력/평균값을 업데이트) → 실제 추론 시점에 보이는 값과 정확히 일치

### 핵심 포인트
- **Weibull 분포** 사용: "다음 사건까지 걸리는 시간"을 모델링할 때 표준적으로 쓰는 확률분포 (지수분포보다 유연함)
- 노이즈(RSRP 흔들림, Weibull 샘플링)도 완전 무작위가 아니라 **그 UE의 상태(Persona, 누적 이력)에 종속**되어 있음
- 결과적으로 데이터는 "**이산적인 타입(persona×서비스종류×이동성)** + **그 안에서의 연속적인 노이즈**"로 이루어짐

## 2. Fine-tuning용 데이터는 어떻게 생성하나? — `gen_realish_csv.py`

### 한 줄 요약
**진짜 실측 데이터가 아니라, "합성 모델이 틀리게 배운 상황"을 인위적으로 만들어서, fine-tuning 파이프라인이 실제로 작동하는지 검증하기 위한 DRY-RUN용 데이터**입니다.

### 왜 실측 데이터를 안 쓰고 이런 걸 만드나
- 아직 라이브 네트워크에서 RRC-INACTIVE 전환이 실제로 돌지 않아 진짜 라벨을 수집할 수 없음
- 실험실(lab) UE로 똑같은 절차를 반복하면 → 매번 거의 똑같은 stat[]/라벨 값만 나옴 → `preprocess.py`가 중복 제거하면 사실상 1개 행만 남음 → 학습 신호가 0
- 그래서 "**진짜처럼 보이되, 합성 모델의 사전지식과는 의도적으로 다르게 어긋난(shift)**" 데이터를 만들어서, "fine-tuning 기능 자체가 제대로 작동하는지"만 증명하는 용도

### 생성 알고리즘
`synth_data_gen.py`와 달리 **UE의 시간에 따른 연속 이력 없이, 행(row) 하나하나를 독립적으로 생성**합니다.

1. 5QI를 하나 뽑고, 그에 딸린 프로파일(평균 지속시간, GBR 여부, 원인 등)을 가져옴
2. 과거 이력(`seq[]`)은 0~10개 사이 랜덤 길이로 "콜드 스타트"부터 채움 (한 UE의 연속된 실제 이력이 아니라 그때그때 랜덤 생성)
3. **라벨 생성이 핵심**: 정상적인 방식으로 기본 지속시간을 뽑은 뒤,
   ```
   최종 라벨 = 기본값 × dur_scale(배율) + rsrp_bias × (75 - RSRP)
   ```
   이렇게 **"합성 모델이 모르는 새로운 규칙"**을 라벨에 강제로 주입합니다. `dur_scale`(기본 2.2배 등)로 전체적인 크기를 바꾸고, `rsrp_bias`로 "RSRP와 지속시간의 관계"까지 기존 모델이 학습하지 못한 새로운 패턴으로 바꿔버림.
4. `--lab-mode` 옵션: 진짜 실험실 UE는 AMBR/RNA 설정을 바꿀 수 없으므로, 이 값들을 상수로 고정 (5QI/RSRP/시간/유휴시간만 변하게) → 실제 lab 수집 상황을 더 비슷하게 흉내

### 5,000 UE와의 차이 (중요)
- `synth_data_gen.py --ues 5000`: **5,000명의 가상 UE**를 시뮬레이션 → 각 UE가 여러 세션을 겪으며 총 수만 개의 행 생성
- `gen_realish_csv.py --n 3000`: UE 개념이 아니라 **3,000개의 독립적인 스냅샷 행**을 그냥 직접 생성 (한 UE가 시간에 따라 여러 세션을 겪는 구조가 아님)

### 사용 목적
"모델을 실제로 더 똑똑하게 만드는 것"이 아니라, **"fine-tune 기능(warm-start + freeze + early-stop + export)이 배관 상 제대로 연결되어 있는지"**를 검증하는 리허설입니다. 진짜 실측 데이터가 들어오면 이 스크립트가 만든 CSV 대신 그 자리에 실측 CSV를 넣으면 됩니다.

## 3. `evaluate.py`는 어떻게 평가하는가 — 평가 지표와 의미

### 한 줄 요약
**"학습된 모델이 그냥 찍는 것보다 나은가?"**, **"이 정도 feature만으로 낼 수 있는 최선(오라클)에 얼마나 가까운가?"**를 숫자로 채점합니다. 데이터 자체를 검증하는 게 아니라 **모델(학습 결과물)의 품질**을 검증하는 것입니다.

### 두 갈래로 나눠서 평가

#### (A) `resume_prob` — 분류 문제 (60초 안에 재접속하나 여부)
| 지표 | 의미 |
|---|---|
| **AUROC** | 무작위 정답/오답 쌍 중 모델이 올바른 순서로 점수를 매기는 비율. 0.5=랜덤, 1.0=완벽 |
| **PR-AUC** | 양성(재접속함)이 적을 때 AUROC보다 더 엄격하게 보는 지표 |
| **ECE** | Calibration 오차. 모델이 "80% 확률"이라 말한 것들이 실제로 80% 맞는지 확인 (낮을수록 좋음) |
| **Precision/Recall/F1** | 임계값(0.6) 기준으로 실제 keep/defer 결정을 내렸을 때의 정확도 |

#### (B) `resume_time` — 회귀 문제 (몇 초 후에 재접속하나, 양성 케이스만)
3개의 **비교 기준선(baseline)**과 모델을 나란히 놓고 MAE(평균 절대 오차, 초 단위)로 비교:

| Baseline | 방식 | 의미 |
|---|---|---|
| **naive** | 전체 평균값으로 통일 찍기 | "아무 생각 없이 찍었을 때" |
| **persistence** | 이 UE의 과거 평균 지속시간을 그대로 예측 | "직전 패턴을 그대로 반복한다고 가정했을 때" |
| **oracle** | feature 조합별 그룹 평균 (아래 설명) | "이 정도 feature 정보만으로 낼 수 있는 이론적 최선" |

**"모델의 MAE가 naive/persistence보다 낮아야 한다"**가 최소 합격선입니다 (`verdict.beats_naive`, `beats_persistence`).

### 오라클(oracle)과 커버리지(coverage)
- 오라클 = "고급 모델 없이 feature 조합별 평균만 룩업테이블로 써도 이 정도는 맞춘다"는 기준선
  - core3 그룹 = `(5QI, RSRP구간, 성공률구간)` 조합
  - full5 그룹 = core3 + `(DRB개수, GBR여부)` 추가
- 단, 그 조합에 학습 데이터가 **30개 미만**이면 신뢰 못 하므로 전체 평균으로 대체
- **커버리지(coverage)** = 검증 데이터 중 "신뢰 가능한 오라클 값이 있는" 비율. **낮으면 오라클 비교 자체의 신뢰도가 떨어짐** (특히 실측 데이터처럼 표본이 적을 때 꼭 확인해야 함)
- `model vs oracle` gap이 작다 = "지금 feature 구성으로 낼 수 있는 한계치에 거의 다 왔다"는 뜻. gap이 크면 "feature를 더 추가하거나 데이터를 늘리면 개선 여지가 있다"는 뜻

### 타이머 정책 관점 지표
- **premature-release(조기 해제)**: 실제보다 타이머를 짧게 잡아서 UE가 다시 풀 RRC 설정을 해야 하는 비율
- **wasted-hold(과잉 유지)**: 실제보다 타이머를 길게 잡아서 gNB가 리소스를 낭비하는 시간/비율
- 실무적으로는 "모델이 naive/persistence보다 이 두 값을 얼마나 줄이는가"가 결국 이 AI 기능의 존재 이유

### 결과물
`eval_report.txt`(텍스트) + PNG 3종(예측-실제 산점도, baseline MAE 막대그래프, 모델-오라클 그룹 비교)

## 4. `train.py`의 결과는 무엇을 의미하나 — 학습과 fine-tuning의 차이

### `train.py`가 하는 일
GRU(순환신경망, 이력 seq[] 처리) + MLP(고정 특성 stat[] 처리)로 구성된 **아주 작은 신경망(파라미터 1,266개)**을 경사하강법으로 학습시킵니다.

```
GRU(2→16) : seq[10][durationSec, resumeCause] 처리
MLP(14→16): stat[14] 처리
결합(32) → head_prob(재접속 확률) / head_time(재접속까지 걸리는 시간)
```

**"학습해서 data[]들에 대한 가중치를 수정하는 것"이 맞습니다** — 정확히는:
- 각 layer의 **가중치 행렬(weight)과 편향(bias)** 수치를 조금씩 조정
- "정답(라벨)과 예측값의 차이(loss)"가 줄어드는 방향으로 반복 조정 (Adam optimizer)
- 이 조정된 최종 가중치가 `model.pt`에 저장되고, 나중에 `export_weights.py`가 이를 C++용 `VccbAiWeights.h`로 변환

### 결과가 의미하는 것
- 학습 도중 매 epoch마다 Train/Val loss가 출력되는데, **Val loss가 계속 낮아지다가 어느 시점부터 더는 안 낮아지면** 그 시점의 가중치가 "가장 일반화가 잘 된" 상태로 저장됨 (`best_state`)
- 학습이 끝나면 자동으로 `metrics.py`의 동일한 지표(AUROC, MAE vs baseline)를 콘솔에 출력 — **`evaluate.py`와 완전히 같은 채점 방식**을 이미 내장하고 있음

### 일반 학습(Full training) vs Fine-tuning의 차이

| 구분 | 일반 학습 (기본) | Fine-tuning (`VCCB_AI_FINETUNE=1`) |
|---|---|---|
| 초기 가중치 | 무작위 초기화 (`xavier_uniform`) | **기존 model.pt를 불러와서 이어서** 학습 (warm-start) |
| Learning Rate | 1e-3 (큼) | 2e-4 (작음, 기본값) |
| Epoch 수 | 50 | 15 (기본값, 적음) |
| Early Stop | 기본 꺼짐 | 기본 켜짐 (patience=5) — val loss가 5번 연속 안 좋아지면 중단 |
| GRU/MLP 동결 옵션 | 없음 | `VCCB_AI_FREEZE_GRU=1` — GRU/MLP는 그대로 두고 출력 head만 미세조정 가능 |
| 목적 | 처음부터 전체 패턴을 배움 | **이미 배운 것(synthetic 사전지식)을 최대한 유지하면서, 소량의 새 데이터(real-ish/실측)에 맞춰 살짝만 보정** |

### 왜 이렇게 구분하나 (Catastrophic Forgetting 방지)
실측 데이터는 양이 적습니다(수백~수천 행). 만약 이 적은 데이터로 처음부터(무작위 초기화) 다시 학습시키면:
- 합성 데이터로 배운 폭넓은 패턴을 다 잊어버리고
- 적은 실측 데이터에만 과적합(overfitting)됨

그래서 fine-tuning은:
1. **낮은 학습률**로 아주 조금씩만 가중치를 바꾸고
2. **적은 epoch + early stopping**으로 너무 많이 바뀌기 전에 멈추고
3. 필요하면 **GRU/MLP는 고정**하고 마지막 head(출력층)만 미세조정

→ **"기존 지식 위에 새 정보를 살짝 얹는" 점진적 학습**이며, "완전히 새로 배우는" 일반 학습과 근본적으로 다릅니다.

## 전체 파이프라인 한눈에 보기

```
[Phase-1: 합성 데이터로 기본 지식 습득]
synth_data_gen.py (가상 UE 시뮬레이션)
   → preprocess.py → train.py (무작위 초기화, 50 epoch)
   → evaluate.py (naive/persistence/oracle 대비 최소 합격선 확인)

[Phase-2: 소량의 real-ish/실측 데이터로 미세조정]
```
